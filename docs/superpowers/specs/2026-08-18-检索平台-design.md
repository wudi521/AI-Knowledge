# 设计文档:检索平台(语义理解 + 改写拆解 + 混合检索 + 重排 + 权限过滤)

> 日期:2026-08-18 · 状态:用户已确认(全面/准确/业务效果优先,非 demo)
> 前置文档:《3-PRD产品需求文档.md》(闭环②/BR-007/M3)、《AI客服知识库系统-原型.html》(retrieval 页)、《上下文交接.md》
> 范围:PRD 阶段 1 的检索平台(retrieval-server 48086);证据平台(M4)与对话工作台(M5)为后续轮次

## 1. 背景与目标

知识入库闭环已完成:文档 → 解析/切分 → 抽取 → 审核 → 发布,数据已在 MySQL/Milvus/ES 三处(发布后)。但**没有任何东西能查这些数据**——检索是"问答服务闭环"的第一步,让已发布知识真正可用。

**成功标准**:
- 中文问题(如"碎屏能免费修吗")能召回正确的已发布 chunk,语义检索有效(ik 分词 + 向量)
- 检索链路完整:语义理解 → 改写/拆解 → 混合检索(BM25+向量)→ RRF 融合 → 重排 → 权限/状态过滤
- 结果只来自"已发布"且"当前用户可见"的知识
- 检索测试页完整展示各环节结果(意图/改写变体/双通道/重排),业务可用非 demo

## 2. 架构

```
retrieval-server(48086) ← 新增主战场
  SearchController → SearchService(编排) 
    ├─ QueryAnalysisService  (LLM 语义理解/改写/拆解, 调 modelApi.chat)
    ├─ Bm25Searcher          (ES ai_chunk_bm25, ik 分词, tenant/kb/status 过滤)
    ├─ VectorSearcher        (Milvus ai_chunk_vector, embedding 变体, tenant/kb 过滤)
    ├─ RrfMerger             (RRF 融合)
    ├─ Reranker              (modelApi.rerank, BGE-reranker-v2-m3)
    └─ ResultFilter          (knowledgeApi.getVisibleKbIds + ingestionApi.getChunkPublishMap)
model-server(48091)      + /rerank(BGE-reranker-v2-m3);复用 /embedding /chat
knowledge-server(48084)  + RPC getVisibleKbIds(userId)(复用 KnowledgePermissionHelper)
ingestion-server(48085)  + RPC getChunkPublishMap(chunkIds)(批量 PUBLISHED 判定)
ES                       ik 插件 + 重建 ai_chunk_bm25(ik_max_word 分词)
```

**检索口径(对齐 BR-005)**:只召回 `status=PUBLISHED` 的 chunk;ES 侧 filter, Milvus 侧(Milvus 无 status 字段)召回后经 ingestion RPC 判定过滤。

## 3. 检索流程(端到端)

```
输入 query
  → ① QueryAnalysisService: LLM 输出 JSON
      { intent: "WARRANTY", entities: ["X100 Pro","碎屏"], rewrites: ["碎屏 免费 维修","碎屏保修政策","屏幕碎裂 售后"], sub_questions: [] }
  → ② 检索变体 = 原句 + rewrites(无改写则仅原句); 复杂问题拆解出的子问并入
  → ③ 双通道并行召回(各 TopK=20):
       BM25: ES bool(must: content match ik_smart; filter: tenant_id, kb_id∈可见, status=PUBLISHED)
       向量: rewrites 逐条 embedding → Milvus search(filter tenant/kb) → 合并去重
  → ④ RRF 融合: score = Σ 1/(k+rank), k=60 → Top20 候选
  → ⑤ 重排: modelApi.rerank(query, 候选内容) → 按相关性分排序 → Top5
  → ⑥ 过滤: 剔除不可见知识库 chunk(权限)+ 非 PUBLISHED chunk(状态)
  → ⑦ 返回 Top5: chunk 内容/来源文档/版本/rerank 分/RRF 分/命中通道
```

**降级(业务效果优先, 不允许空手而归)**:
- LLM 理解/改写失败 → 用原句检索(仅记日志)
- 重排失败 → 用 RRF 顺序
- 单通道失败 → 用另一通道结果
- 过滤后不足 Top5 → 返回实际条数(不凑数,不返回越权/未发布数据)

## 4. 接口设计

### 4.1 retrieval 检索 API(admin)

`POST /admin-api/retrieval/search`

```json
请求: { "query": "碎屏能免费修吗", "kbIds": [1], "topK": 5 }
响应: {
  "query": "碎屏能免费修吗",
  "analysis": { "intent": "WARRANTY", "entities": ["碎屏"], "rewrites": ["碎屏 免费 维修", ...], "subQuestions": [] },
  "results": [ {
      "chunkId": 1956, "content": "...", "documentId": 23, "documentName": "产品售后政策",
      "versionNo": "V1", "score": 0.93, "rrfScore": 0.021, "channels": ["bm25","vector"]
  } ]
}
```

### 4.2 新增跨模块 RPC

| 接口 | 提供方 | 说明 |
|---|---|---|
| `ModelApi.rerank(query, List<String> passages) → List<Float>` | model-server | LM Studio `/v1/rerank`,BGE-reranker-v2-m3(已加载) |
| `KnowledgeApi.getVisibleKbIds(userId) → Set<Long>` | knowledge-server | 复用 KnowledgePermissionHelper(super_admin 返回全部) |
| `IngestionApi.getChunkPublishMap(chunkIds) → Map<Long,Boolean>` | ingestion-server | 批量判定 chunk 是否 PUBLISHED |

### 4.3 前端

- 新页**「检索测试」**(菜单 6762):输入问题 + 可选知识库 → 检索
  - 展示区:**意图标签**、实体、**改写变体**、子问题(如有)
  - 结果 Top5 卡片:内容(**命中关键词高亮**)、来源文档/版本、分数(rerank)、命中通道(BM25/向量 双徽标)
  - 每次检索展示"各通道召回数"统计(业务可观测)
- 知识库列表每行加「检索测试」按钮 → 跳转检索页并带入 kbId
- 遵循既有前端规范(主题色/formatDateTime/弹窗规范)

## 5. 基建:ES ik 分词

- 安装 ik 插件(与分析器版本匹配 ES 8.13.4, 如 ik 8.13.x release, offline zip 解压到插件目录)
- 重建 `ai_chunk_bm25`:mapping `content` 用 `ik_max_word`(索引)与 `ik_smart`(搜索);保留 chunk_id/tenant_id/kb_id/status keyword
- 重建后存量已发布 chunk 需重灌索引(从 MySQL 读已发布 chunk 重写 ES;或删除索引由 indexVersion 重写——**采用从 MySQL 重建**:写一次性重灌脚本/接口)
- ⚠️ 重建期间检索不可用?→ 先建新索引名 `ai_chunk_bm25_v2`,灌完后切 alias,零停机

## 6. 权限与租户

- 检索必须过:租户(框架 TenantBaseDO/ES 查询带 tenant_id)+ 知识库可见角色(knowledge RPC)+ chunk 已发布(ingestion RPC)
- super_admin 直通可见知识库过滤(但 tenant 隔离仍生效)
- 越权访问 0 容忍:过滤是"剔除"而非"返回空结果",保证不泄露

## 9. 已知权衡

- 单次检索含 2~4 次 LLM/embedding/rerank 调用,CPU 推理下 5~20 秒——业务可接受,后续可缓存意图分析(同 query 短时缓存)
- rerank 候选上限 Top20(避免大列表拖慢)
- 检索质量依赖已发布数据质量;未发布内容不可检索是特性(审核门禁的意义)
