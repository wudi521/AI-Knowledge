# 设计文档:知识库槽位检测(问题条件抽取 + 知识库固定槽位定义)

> 日期:2026-08-18 · 状态:用户确认(修订版: 槽位绑知识库;evidence 侧先行;chat 多轮闭环由另一任务承接)
> 背景:证据平台 EV-01~EV-06 已交付。演示"我的手机坏了,可以免费维修吗?"暴露问题——问题缺品牌/故障性质/购机时间等关键条件时,系统不反问、直接给出"如果…如果…"的骑墙回答。另,既有产品/品牌提取写死在检索提示词里,换场景不可复用。
> 定位(与用户对齐后的目的): 槽位是**知识库文档的"条件维度"**。客服问题本质是"条件 → 结论"匹配("X100 Pro 用 2 个月非人为故障" 匹配条款 "在保期内非人为故障 → 免费维修")。槽位检测把问题的关键条件结构化,缺了才反问;抽到的值结构化输出+落库,为后续**喂回检索做定向**(本轮不做)与 chat 多轮闭环(另一任务)留好接口。
> 范围: knowledge-server(槽位定义表 + admin CRUD + RPC)+ evidence-server(检测组件 + evaluate 步骤 0 + 落库);**不碰** retrieval(纯搜索)、**不碰** chat。槽位定义**动态数据驱动**: 一个知识库一组固定槽位, 换库/加属性 = 插行/改行, 无需改代码或提示词。

---

## 1. 背景与目标

**问题一:问题条件缺失无感知。** 客户问"我的手机坏了,可以免费维修吗?"——品牌、故障性质、购机时间全缺。当前管线单轮直答,基于通用条款给出分支式回答,客户无法据此行动。

**问题二:槽位必须绑知识库。** 槽位不是全局"场景",而是**某个知识库的文档围绕什么条件组织**的。售后政策知识库的文档按"品牌/故障性质/购机时间"区分条款;物流知识库按"订单类型/区域/物流状态"区分;通用保修知识库可能不分品牌。槽位由**知识库所有者**定义,一个知识库一组固定槽位——反问只在"该库的文档确实区分这些条件"时发生,避免无效反问。

**成功标准**:
- `POST /evidence/evaluate` 输入歧义问题(kbIds 指向已配槽位的知识库)→ `answerable=false` + 结构化反问(`missingSlots` + `clarifyQuestion`),**不触发检索**, 仍落库留痕
- 槽位定义存 `ai_knowledge_base_slot`(绑 `ai_knowledge_base`, 租户隔离), knowledge 提供 admin CRUD API;运行期增删改/启停**立即生效**
- 检测 LLM 失败 / 无槽位定义 / kbIds 为空 / 租户缺失 / 总开关关闭 → **降级为不检测**, 永不阻断原管线
- 槽位齐全的问题 → 照常走检索/评估, 原品牌一致性门禁**照常生效**(互补不冲突: 检测管"缺条件", 门禁管"条件与证据不符")
- 抽取结果结构化输出(`extractedSlots`)并落库, 供后续检索定向/chat 合并复用

## 2. 架构(evidence 侧新增步骤 0, 原管线不动)

```
knowledge-server(4808x)     知识库 + 槽位配置(数据拥有方)
  AiKnowledgeBaseSlotController → Service → Mapper(ai_knowledge_base_slot)
  KnowledgeApi.getSlotDefinitions(kbIds)   ← Feign 暴露

evidence-server(48087)
  EvidenceEvaluateController → EvidenceService(evaluate 编排)
    ├─ 0. SlotDetector(新增)  知识库槽位检测(检索之前)
    │     ├─ 条件: slot.enabled && kbIds 非空 && 目标 KB 存在启用槽位定义
    │     ├─ 加载: KnowledgeApi.getSlotDefinitions(kbIds) → 按 slot_code 并集去重(同编码同语义)
    │     ├─ LLM: 注入"槽位定义 JSON + 问题" → {applicable, extracted, missing}
    │     ├─ 失败/解析失败 → 降级不检测(log.warn, 走原流程)
    │     └─ applicable=true 且 missing 非空 → answerable=false + 反问, 不检索, 落库, 返回
    ├─ 1. EvidenceAssembler   检索结果(Feign retrieval.search) → Evidence 列表
    ├─ 2. EvidenceDeduplicator  内容相似度去重
    ├─ 3. ConflictDetector     同主题证据矛盾判定
    ├─ 4. SufficiencyJudge     充分性判定(配置化规则 + 分数融合)
    ├─ 5. AnswerPipeline       生成回答 + Claim 逐句验证
    └─ 6. EvidenceRecorder     判定结果落库 ai_evidence_eval + ai_evidence
knowledge-api(Feign)      getSlotDefinitions(kbIds) → List<KnowledgeSlotDefinitionDTO>
model-server(48091)      Feign: /chat(检测与生成共用模型网关)
```

**单次 LLM 调用设计**(与 `QueryAnalysisService` 结构化输出模式一致):
- 提示词模板固定(通用"抽取以下槽位"结构), 槽位定义序列化为 JSON 注入(**数据驱动, 不写死任何槽位/场景**)
- 输出 `{"applicable": true|false, "extracted": {"brand": "苹果13", ...}, "missing": [{"code":"faultType","name":"故障性质"}]}`
- `applicable=false`(问题与槽位集对应领域无关, 如"你好")→ missing 视为空 → 放行
- missing 判定由 LLM 给出, 但**代码兜底校验**: required 槽位在 extracted 中缺失/空值 → 计入 missing(双保险)

## 3. 数据模型

### ai_knowledge_base_slot(新增, knowledge 模块, 租户隔离 TenantBaseDO)

| 列 | 类型 | 说明 |
|---|---|---|
| id | bigint PK | 编号 |
| kb_id | bigint | 所属知识库编号(逻辑关联 ai_knowledge_base.id) |
| slot_code | varchar(64) | 槽位编码(如 brand/faultType/purchaseTime), 非空 |
| slot_name | varchar(64) | 槽位名(如 品牌型号), 非空 |
| description | varchar(500) | 抽取说明(喂给 LLM 的定义), 非空 |
| required | bit(1) | 是否必填(1=缺则反问, 0=选填不反问) |
| sort | int | 排序(组反问句顺序) |
| status | tinyint | 启停: 0=启用 1=禁用(CommonStatusEnum) |
| creator/create_time/updater/update_time/deleted/tenant_id | - | 审计字段(惯例) |

约束: 唯一键 `uk_kb_slot(kb_id, slot_code, deleted)`(同知识库内槽位编码唯一)。

### ai_evidence_eval(增量 3 列)

| 列 | 类型 | 说明 |
|---|---|---|
| slots | json | 本次抽取的槽位值 {"brand":"苹果13"} |
| missing_slots | json | 缺失必填槽位 [{"code":"faultType","name":"故障性质"}] |
| clarify_question | varchar(500) | 拼接好的反问句(answerable=false 且因缺槽位时填充) |

## 4. 接口

### knowledge admin 槽位 CRUD(权限 `knowledge:kb-slot:*`)

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /knowledge/kb-slot/create | 创建(kbId/槽位/必填/排序/启停) |
| PUT | /knowledge/kb-slot/update | 更新 |
| DELETE | /knowledge/kb-slot/delete?id= | 删除 |
| GET | /knowledge/kb-slot/get?id= | 详情 |
| GET | /knowledge/kb-slot/page | 分页(kbId/槽位/启停筛选) |

### KnowledgeApi RPC 新增

`GET/POST /knowledge/get-kb-slots` → `CommonResult<List<KnowledgeSlotDefinitionDTO>>`(kbId/slotCode/slotName/description/required/sort; 仅启用行, 按 kb_id+sort 排序)

### evidence evaluate 响应增量字段(EvidenceEvaluateRespVO + EvidenceEvaluateRespDTO 同步)

| 字段 | 类型 | 说明 |
|---|---|---|
| slotKbId | Long | 参与检测的知识库编号(多库并集时取首个; 未检测为 null) |
| extractedSlots | List\<SlotValueVO{code,name,value}\> | 从问题中抽取的槽位值(审计/后续合并用), value 为抽取到的原文 |
| missingSlots | List\<SlotValueVO{code,name,value}\> | 缺失的必填槽位, **value 恒为 null**(与 extractedSlots 复用同一 VO 类型) |
| clarifyQuestion | String | 拼好的反问句, 如"请补充以下信息:品牌型号、故障性质、购机时间"(由缺失槽位名按 sort 升序拼接) |

语义: `answerable=false` 且 `missingSlots` 非空 ⇒ 因缺条件反问;`refusalReason` = "需补充信息:品牌型号、故障性质、购机时间"。

## 6. 降级与边界

| 场景 | 行为 |
|---|---|
| slot.enabled=false | 跳过检测, 走原流程 |
| kbIds 为空(检索全部可见库) | 跳过检测(log note; 产品流为 KB 定向: evidence evaluate 与 chat 均带 kbIds) |
| 目标 KB 无启用槽位定义 | 跳过检测 |
| 检测 LLM 调用异常/超时 | log.warn + 跳过检测(原流程) |
| LLM 输出 JSON 解析失败 | log.warn + 跳过检测(原流程) |
| applicable=false(问题与槽位领域无关) | 放行(不反问) |
| 槽位齐全 | 正常检索;原品牌一致性门禁照常生效 |
| 多 KB 并集 | 按 slot_code 去重(同编码同语义);首个出现行的 kb_id 记为 slotKbId |
| 反问落库 | ai_evidence_eval 1 行(evidence_count=0), 不写 ai_evidence 证据行 |

**错误码**: knowledge `KNOWLEDGE_KB_SLOT_NOT_EXISTS`(admin CRUD 用)。

| 编号 | 步骤/输入 | 期望 |

## 8. 领域无关性保证

- 提示词模板固定(通用"抽取以下槽位"), 槽位集全部来自 `ai_knowledge_base_slot` 行
- 新增知识库/场景 = 给该 KB 配行; 删除/禁用 = 启停/删除行; 无需改代码或提示词
- 检测组件不感知"售后/保修"业务词汇, 一切由 description 定义驱动
- 槽位定义归 knowledge(数据拥有方), 检测逻辑归 evidence(判定管线), 边界清晰

## 9. 后续衔接(不在本设计范围)

- **抽取值喂回检索**: `extractedSlots` 已结构化输出+落库, 后续检索层可按条件定向(如品牌过滤)或加权——本轮 retrieval 不动
- **chat 多轮闭环**(另一任务): ChatPipeline 收到 missingSlots/clarifyQuestion → 回复反问并保持 ACTIVE(不转人工); ai_conversation 累积槽位值; 下一轮将已抽取值并入 evaluate 请求合并重评估
- **GUI**: 知识库槽位配置页(knowledge 管理端)+ 证据面板反问卡片, 已预留结构化字段
