# 设计文档:槽位自动生成(LLM 总结知识库内容 → 自动建槽位 + 用户管理)

> 日期:2026-08-19 · 状态:用户确认(新建时 + 发布后自动 + 手动触发; 用户编辑后保护不覆盖)
> 前置:槽位检测已交付(ai_knowledge_base_slot + SlotDetector + evaluate 步骤 0 反问, 见《2026-08-18-槽位检测-design.md》)。本设计为其补齐"槽位定义从哪来"——当前槽位完全靠人工配置, 本设计让 LLM 从知识库已发布内容自动总结生成, 用户随时可管理。
> 模式复用:知识模块已有 `IntentSummarizer`(LLM 总结已发布内容 → 覆盖式写 LLM_AUTO 意图, MANUAL 保留, 发布后 afterCommit 异步触发 + 手动 summarize 重跑, 失败不阻断)——本设计完全复用该模式。
> 范围: knowledge-server(48084); **不碰** evidence(消费侧无改动)、retrieval、chat。前端面板(yudao-ui 不在本仓库)仅预留接口。

---

## 1. 背景与目标

槽位检测需要槽位定义, 目前只能人工在 `/knowledge/kb-slot/*` 一条条配置。售后知识库的文档围绕"品牌型号/故障性质/购机时间"组织, 物流知识库围绕"订单类型/区域/物流状态"——**这些条件维度本质上可以由 LLM 从知识库内容中总结出来**。

**成功标准**:
- 新建知识库时自动触发一次生成(空库无内容 → 优雅跳过, 不报错)
- 发布文档后自动触发生成(afterCommit 异步, 与意图总结同点)
- 手动 `POST /knowledge/kb-slot/summarize?kbId=` 可随时重跑(覆盖 LLM_AUTO, MANUAL 保留)
- 用户手动编辑过(update)的 LLM_AUTO 槽位 → source 翻转 MANUAL, 后续自动生成不再覆盖
- 生成/总结任何失败只 log.warn, 绝不阻断发布/创建流程; 可手动重跑
- evidence 侧零改动(自动生成的槽位与手动配置的完全等价, SlotDetector 照常消费)

## 2. 架构

```
knowledge-server(48084)
  AiKnowledgeBaseSlotController
    ├─ /knowledge/kb-slot/*       用户管理 CRUD(已有; create 强制 MANUAL, update 翻转保护)
    └─ /knowledge/kb-slot/summarize  手动重跑(新增; 同步执行返回生成数)

  SlotSummarizer(新增, 镜像 IntentSummarizer)
    ├─ summarizeByKb(kbId)        同步(手动用)
    ├─ summarizeByKbAsync(kbId)   异步(新建/发布用; 单线程守护池 + TtlRunnable 传租户)
    ├─ PublishedContentCollector(新增共享组件, 原 IntentSummarizer 采样逻辑抽出)
    │     └─ collectPublishedContent(kbId): ≤40 片段 × 200 字, 跨版本均衡采样
    ├─ LLM 总结: 内容 → {slots:[{code,name,description,required,sort}]}
    └─ slotService.replaceAutoSlots(kbId, slots)

  AiKnowledgeBaseServiceImpl.createAiKnowledgeBase   → 末尾 summarizeByKbAsync(kbId)
  AiDocVersionServiceImpl.publish                    → afterCommit 追加 summarizeByKbAsync(doc.getKbId())

  SlotService.replaceAutoSlots(kbId, slots)  @Transactional
    ├─ 逻辑删除该 KB 全部 source=LLM_AUTO
    └─ 批量插入新槽位(source=LLM_AUTO, status=0, kbId 强制)
model-server(48091)  Feign: /chat(意图与槽位总结共用模型网关)
```

## 3. 数据模型

`ai_knowledge_base_slot` 增量 1 列(ALTER TABLE):

| 列 | 类型 | 说明 |
|---|---|---|
| source | varchar(16) NOT NULL DEFAULT 'MANUAL' | 来源: LLM_AUTO(总结器生成, 可被覆盖重写)/ MANUAL(用户创建或编辑过, 受保护) |

对齐 `ai_intent.source` 语义(已有)。

## 4. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | /knowledge/kb-slot/summarize?kbId= | LLM 总结该知识库槽位(覆盖 LLM_AUTO, MANUAL 保留); 返回生成数; 无已发布内容返回 0; 失败返回 -1。权限 `knowledge:kb-slot:update` |

`KnowledgeApi.getSlotDefinitions` 不变(自动生成的槽位与手动等价, evidence 零改动)。

## 6. 提示词要点(SlotSummarizer SYSTEM_PROMPT)

- 角色: 知识库条款分析师; 根据已发布内容总结该库条款/文档围绕的**条件维度(槽位)**
- 输出: `{"slots":[{"code":"brand","name":"品牌型号","description":"客户产品的具体品牌/型号...","required":true,"sort":1}]}`
- 要求: code 英文蛇形且唯一; required = "缺了该信息是否影响准确作答该库问题"(售后库品牌/故障/时间必填; 通用库可全选填); 只总结库中实际区分的维度, 不编造; 2~8 个
- 内容为空 → 跳过(返回 0)

## 7. 降级与边界

| 场景 | 行为 |
|---|---|
| 新建知识库(无内容) | summarizeByKbAsync → 无已发布内容 → log.warn + 返回 0, 不阻断创建 |
| 发布流程中 LLM 失败 | 仅 log.warn, 发布照常完成; 可手动 summarize 重跑 |
| LLM 输出解析失败/无可解析槽位 | log.warn + 返回 -1, 保留旧槽位 |
| replaceAutoSlots 部分失败 | 事务回滚, 旧 LLM_AUTO 保留, 不出现半新半旧 |
| 用户 update 自动槽位 | source 翻转 MANUAL, 下次 summarize 不覆盖 |
| 用户停用(status=1)自动槽位 | 算编辑 → 翻 MANUAL, 自动生成不再重建(**永久屏蔽的推荐方式**) |
| 用户 delete 自动槽位 | 逻辑删除; 文档化: 下次 summarize 可能重新建议同名槽位(因内容仍在), 想永久移除用"停用" |
| 租户 | 与意图一致: 异步任务 TtlRunnable 传递租户上下文 |

## 8. 验证(对齐仓库 EV 脚本风格)

| 编号 | 步骤/输入 | 期望 |
|---|---|---|
| S-01 | 售后库(已有内容)手动 `POST /knowledge/kb-slot/summarize?kbId=1` | 返回 3 左右; ai_knowledge_base_slot 新增 source=LLM_AUTO 的槽位(brand/faultType/purchaseTime 或等价) |
| S-02 | update 其中一个自动槽位(如改 description) → 再 summarize | 该槽位 source 已翻 MANUAL 且内容保留; 其他 LLM_AUTO 被覆盖重写 |
| S-03 | 新建知识库 → 上传/发布文档 | 发布后异步自动生成槽位(source=LLM_AUTO), 不阻断发布 |
| S-04 | 自动生成后跑 EV-07(我的手机坏了, kbIds=该库) | 反问生效(与手动配置等价) |
| S-05 | 停用 1 个自动槽位 → 再 summarize | 不重建该槽位(MANUAL 保护) |
| S-06 | 落库核对: source 列/生成时间/数量 | 正确 |
