## 1. 背景与目标

检索平台能"找到证据并生成总结",但**缺少"能否作答"的判定**:
- 证据够不够?够充分才允许回答
- 证据之间是否矛盾?有冲突必须禁止/转人工
- 生成的回答是否每一句都有证据支撑?无据断言必须拦截

证据平台把这些做成**领域无关的通用管线**:任何行业(客服/医疗/法律/政务…)的知识库,只要产出"检索结果",就走同一套证据判定,充分性标准用配置表达而非行业硬编码。

**成功标准**:
- `POST /evidence/evaluate` 输入问题 → 输出结构化判定:answerable / confidence / evidence 列表 / conflict 标记 / claim 验证结果
- 充分性阈值、实体一致性要求、冲突拦截开关全部 yaml 可配(默认对齐 BR-009/BR-010)
- 冲突证据 → answerable=false;无据断言 → 拦截并重试, 仍失败 → 禁止输出
- ai_evidence 落库留痕(谁/何时/判定/证据/耗时)
- 前端证据面板展示:充分性评分、证据列表(可展开原文)、冲突标记、Claim 逐句结果

## 2. 架构(领域无关的判定管线)

```
evidence-server(48087)
  EvidenceController → EvidenceService(evaluate 编排)
    ├─ EvidenceAssembler   检索结果(Feign retrieval.search) → Evidence 列表
    │    Evidence{chunkId, content, documentName, versionNo, score, products, channel}
    ├─ EvidenceDeduplicator  内容相似度去重(共享/字符重叠 > 阈值合并, 保留高分)
    ├─ ConflictDetector     同主题证据矛盾判定(LLM 结构化, 输出 conflict/reason; 失败按无冲突处理)
    ├─ SufficiencyJudge     充分性判定(配置化规则 + 分数融合 → answerable/confidence/reason)
    ├─ AnswerGenerator      基于证据生成回答(带 [C1] 引用)
    ├─ ClaimVerifier        回答拆断言 → 逐句 SUPPORTED/UNSUPPORTED(重试 ≤2)
    └─ EvidenceRecorder     判定结果落库 ai_evidence(留痕)
retrieval-server(48086)  Feign: /retrieval/search(复用混合检索/品牌门禁)
model-server(48091)      Feign: /chat /embedding /rerank
```

**判定管线(纯流程, 无行业耦合)**:
```
query + kbIds
  → ① 检索(调 retrieval.search) → 候选证据
  → ② 去重(相似内容合并)
  → ③ 冲突检测(同主题矛盾 → conflict 标记)
  → ④ 充分性判定(配置规则 + 分数/数量/实体覆盖融合) → answerable?
      ├─ 充分(≥阈值 且 无冲突) → ⑤ 生成回答 → ⑥ Claim 逐句验证
      │    全 SUPPORTED → 输出 answer + evidence + verdicts
      │    有 UNSUPPORTED → 重试生成(≤2), 仍失败 → 禁止输出(转人工)
      └─ 不充分 / 有冲突 → 不生成回答, 输出 answerable=false + 原因 + 证据列表
  → ⑦ 全部落库 ai_evidence
```

## 3. 充分性判定(通用规则, 全部可配置)

配置块(application yaml, 默认对齐 BR-009):

```yaml
yudao:
  evidence:
    sufficiency:
      answer-threshold: 0.75     # confidence ≥ 0.75 允许作答
      consult-threshold: 0.5     # 0.5~0.75 转人工/补充证据
      min-evidence-count: 2      # 相关证据至少 2 条
      entity-consistency: true   # 问题有产品时, 证据必须覆盖该产品(否则拒绝)
      conflict-block: true       # 存在冲突证据 → 禁止作答
      weights: { top-score: 0.5, evidence-count: 0.3, entity-coverage: 0.2 }
    dedup:
      similarity-threshold: 0.85 # 内容相似度超过则合并
    claim:
      max-retry: 2               # 无据断言重试生成上限
```

**confidence 计算(与行业无关)**:`confidence = Σ weight × 归一化指标`,其中:
- top-score:最高证据分(归一化到 0~1,如 rerank 分经 sigmoid/排名映射——用证据在候选中的相对分数)
- evidence-count:min(证据数/期望数, 1)
- entity-coverage:证据产品覆盖问题产品 = 1,否则 0(无产品要求则 1)
- 存在冲突 → 直接 answerable=false(无论分数)
- 产品不匹配 → 直接 answerable=false(结构化, 与检索平台门禁一致)

## 4. 冲突检测(通用)

- 输入:去重后证据两两组合中,同主题(证据主题相似度高的对)
- 判定:LLM 结构化输出 `{"conflict": true/false, "reason": "...", "pair": [i, j]}`
- 规则兜底:同主题证据中,数值/期限类实体(如 ¥699 vs ¥799)冲突由 LLM 识别;LLM 失败 → 按无冲突处理(保守可配置)
- 输出:conflicts 列表 → SufficiencyJudge 依据 conflict-block 配置决定

## 5. Claim 验证(通用)

- 生成回答后,一次 LLM 调用把回答拆为断言并逐句判定:
  `{"claims": [{"text": "...", "verdict": "SUPPORTED|UNSUPPORTED", "evidenceIndex": 1}]}`
- 全 SUPPORTED → 放行;出现 UNSUPPORTED → 重新生成回答(提示"上次回答有 N 句无据, 请只依据证据"),重试 ≤2
- 仍失败 → answerable=true 但 answer 置 null + claimFail=true(转人工)

## 6. 数据落库(ai_evidence)

```sql
-- 复用已有 ai_evidence 表(若字段不足则增量):
-- id, chunk_id(证据chunk), confidence, verdict(判定: answerable 等), trace_id, ...
```
判定会话留痕:每次 evaluate 生成 trace_id,证据/判定/冲突/claim 全部关联存库(供重放/审计/评测, 对齐 BR-020 链路快照的最小集)。

## 7. 接口

`POST /admin-api/evidence/evaluate`
```json
请求: { "query": "X100 Pro 屏幕碎了能免费修吗", "kbIds": [1], "topK": 5 }
响应: {
  "traceId": "ev-xxx",
  "query": "...",
  "answerable": true,
  "confidence": 0.87,
  "refusalReason": null,          // answerable=false 时的原因(产品不匹配/证据不足/冲突)
  "evidence": [ { "chunkId": 2082, "content": "...", "documentName": "...", "versionNo": "V1",
                  "score": 0.93, "products": ["X100 Pro"], "channel": ["bm25","vector"] } ],
  "conflicts": [ { "evidenceIndexA": 1, "evidenceIndexB": 3, "reason": "..." } ],
  "answer": "很遗憾... [C1]",      // answerable 且 Claim 全通过才返回
  "claims": [ { "text": "...", "verdict": "SUPPORTED", "evidenceIndex": 1 } ],
  "claimFail": false
}
```

## 8. 前端(证据面板)

- 检索测试页下方/或独立"证据评估"区:充分性判定卡片(置信度进度条 + answerable 徽标 + 拒绝原因)
- 证据列表(可展开原文)+ 冲突证据红标 + Claim 逐句(✓ SUPPORTED / ✗ UNSUPPORTED)
- 与检索结果/品牌门禁联动:产品不匹配直接显示拒绝(结构化)

## 9. 实施顺序(单计划)

1. evidence-server 启动 + 接线(Feign: retrieval/model/knowledge)+ yaml 配置块
2. EvidenceAssembler(调 retrieval.search 组装证据)+ EvidenceDeduplicator(相似度去重)
3. ConflictDetector(LLM 结构化冲突判定 + 规则兜底)
4. SufficiencyJudge(配置化规则 + confidence 融合)
5. AnswerGenerator + ClaimVerifier(断言逐句 + 重试)
6. EvidenceController + VO + ai_evidence 落库(EvidenceRecorder)
7. 前端证据面板 + 检索测试页联动
8. 端到端验证:充分作答 / 证据不足 / 冲突 / 产品不匹配 / 无据断言拦截

## 10. 验收要点

| 编号 | 验收标准 |
|---|---|
| EV-01 | 问"X100 Pro 碎屏免费修吗" → answerable=true, confidence≥0.75, 回答带 [C1] 且 Claim 全 SUPPORTED |
| EV-02 | 问苹果13(库内无) → answerable=false, reason=产品不匹配 |
| EV-03 | 构造冲突证据(V1"免费修" vs V2"不免费"同库) → answerable=false, conflicts 非空 |
| EV-04 | LLM 生成含无据句 → 拦截重试 ≤2, 仍失败 → claimFail=true 且 answer=null |
| EV-05 | ai_evidence 落库可查(含证据/判定/冲突/claim) |
| EV-06 | 阈值改 yaml(如 answer-threshold=0.6)立即生效, 判定随之变化 |

## 11. 领域无关性保证

- 零行业硬编码:产品/保修/价格等概念仅作为"通用实体/证据字段"出现, 判定逻辑不看字段含义
- 全部标准可配置(阈值/权重/开关), 换行业只改 yaml 与知识库内容
- 证据/冲突/Claim 均为通用抽象, 客服/医疗/法务/政务同管线
- 输出结构化 + 落库, 供任何下游(对话/评测/审计)消费
