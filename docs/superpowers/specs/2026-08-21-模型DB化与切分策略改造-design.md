# 模型配置数据库化 + 切分策略文档级/插件化/结构化解析 设计文档

> 日期: 2026-08-21 · 状态: 待评审 · 对应需求: 用户 5 条需求(1~4 代码改造, 5 业务评估)

---

## 1. 背景与目标

### 1.1 背景

当前系统存在以下问题:

1. **模型配置双轨**: 模型调用虽有数据库配置(`ai_model_config`), 但实际生效的是 yaml 兜底(`yudao.model.{chat,embedding,rerank}`)。数据库里初始化数据与实际使用的模型不符(deepseek-chat 无 key 每次 401、bge-m3 端口 11434 已废弃等), 每次调用实际走 yaml, 数据库配置形同虚设。
2. **切分策略绑知识库**: `ai_knowledge_base.chunk_strategy` 为知识库级, 同一知识库下不同文档(专利/合同/FAQ)无法用不同策略, 不符合"切分策略基于文档"的业务事实。
3. **切分基于纯文本, 效果上限低**: 解析层只输出纯文本, 标题层级/表格结构/图片位置/段落归属全部丢失; 5 个切分器为正则启发式, 对真实文档(专利/论文/合同)精准度不足; **完全没有图片识别**, 专利等含图文档的内容(图、表、公式)无法被检索。
4. **意图/槽位管理业务价值待评估**: 用户反馈"不好用", 需要业务层面的打磨评估来决定去留, 而非直接改代码。

### 1.2 目标

| 编号 | 目标 | 对应需求 |
|---|---|---|
| G1 | 模型连接配置与成本单价**全部数据库化**, 删除 yaml 中的模型配置段与 yaml 兜底逻辑; 加载时按 type/scenario 从数据库按需加载 | 需求 1、2 |
| G2 | 切分策略从知识库级改为**文档级**, 知识库列表/表单去掉切分策略 | 需求 3 |
| G3 | 切分策略**插件化**(Spring 组件式), 入库管线按文档配置选择策略, 支持参数化; 新增策略=新增类, 不改工厂 | 需求 4 |
| G4 | 解析层升级为**结构化解析**(MinerU + POI + 视觉模型), 支持全部文档类型(PDF/WORD/EXCEL/PPT/IMAGE/MD/TXT), **图片内容生成描述参与向量检索** | 需求 4 |
| G5 | 切分在**保证精准度**的同时保证**上下文连贯性**(标题链注入/相邻合并/父子块/图片上下文绑定) | 需求 4 |
| G6 | 意图/槽位产出**业务评估文档**(价值/痛点/场景适配/改进路径/去留建议), 本轮不改其代码 | 需求 5 |

### 1.3 已确认决策(用户拍板)

1. 图片识别: 用**多模态 LLM 生成图片描述**, 描述文本参与切分和向量检索(图片也要可检索)。
2. 插件化深度: **Spring 组件式插件**(`ChunkSplitter` 接口 + `@ChunkStrategy` 注解 + 容器自动注册)。
3. 意图/槽位: **本轮不改代码**, 产出业务评估文档供后续决策。
4. 成本单价: `yudao.model.pricing.*` **迁入 `ai_model_config` 表**(新增 in/out 每百万 token 单价列)。
5. 解析引擎: **MinerU(中文布局感知, PDF/扫描件) + POI(Office 结构化) + 视觉模型(图片描述/扫描页兜底)** 组合, 企业级生产方案。
6. 扫描件: 用**视觉模型识别扫描页**(MinerU OCR 作兜底)。
7. 知识库 `embed_model` 字段随模型 DB 化一并移除(模型全局配置后无意义; 用户未反对, 列为默认项)。

## 4. 子项目 B: 切分策略文档级 + 插件化 + 结构化解析 + 图片识别

### 4.1 新入库管线(核心架构)

```
上传文档(选切分策略, 可 auto) → ai_document 登记(chunk_strategy + params) → Kafka
  → ingestion 消费
      → ① 结构化解析: MinerU(PDF/扫描) / POI(Office) / 文本(MD/TXT) / 视觉模型(IMAGE 文档)
          → ParsedDocument 结构树(Heading/Paragraph/Table/Image/List, 各元素带页码/序号/父标题链)
      → ② 切分策略插件: SplitterFactory 按文档 chunk_strategy 取切分器(基于结构树切分)
      → ③ 上下文增强: 标题链注入 / 相邻合并 / 图片上下文绑定 / overlap
          → List<Chunk>(content + chunkType + parentId + metadata[页码/章节路径/图片引用])
      → ④ 向量化 → 落 MySQL(REVIEW) → notifyParsed → 审核发布(不变)
```

### 4.2 B1: 切分策略改为文档级

#### 4.2.1 表结构

```sql
-- ai_document 增加文档级切分策略
ALTER TABLE `ai_document`
  ADD COLUMN `chunk_strategy` varchar(32) NOT NULL DEFAULT 'auto' COMMENT '切分策略: auto/structure/parent-child/semantic/policy/faq/table/image' AFTER `file_hash`,
  ADD COLUMN `chunk_strategy_params` varchar(1024) NULL DEFAULT NULL COMMENT '策略参数(JSON, 覆盖默认; 如 {"maxTokens":500,"overlap":1})' AFTER `chunk_strategy`;

-- ai_knowledge_base 移除切分策略与 Embedding 模型(模型全局 DB 化)
ALTER TABLE `ai_knowledge_base`
  DROP COLUMN `chunk_strategy`,
  DROP COLUMN `embed_model`;

-- 存量回填: 文档继承原知识库策略(缺失列删除前先回填)
UPDATE `ai_document` d LEFT JOIN `ai_knowledge_base` k ON d.kb_id = k.id
  SET d.chunk_strategy = IFNULL(k.chunk_strategy, 'auto');
-- 注意: 回填与 DROP 在同一迁移脚本内按顺序执行; 已删除列的历史库需先从备份或 git 历史补列
```

### 4.3 B2: 切分策略插件化

#### 4.3.1 接口升级

```java
/** 通用切分参数(所有策略通用 + 扩展 Map) */
public class SplitParams {
    private int maxTokens = 500;      // 单块上限(token 估算口径沿用 1.5 字符/token)
    private int overlap = 0;          // 句子级重叠数(默认 0)
    private boolean titleChain = true;// 是否注入标题链(默认开)
    private Map<String, Object> extra;// 策略自定义参数
}

public interface ChunkSplitter {
    List<Chunk> split(ParsedDocument doc, SplitParams params);  // 基于结构树切分
    // 策略元数据(key/中文名/描述/默认参数)统一由 @ChunkStrategy 注解提供,
    // SplitterFactory 构造时读取注解注册; 接口不再声明元数据方法, 避免双轨。
}
```

为兼容过渡, 保留 `split(String text, int maxTokens)` 默认方法(内部将文本包装为无结构 ParsedDocument 调用新方法), 存量语义/兜底逻辑不丢。

#### 4.3.2 注解与自动注册

```java
/** 标注在 ChunkSplitter 实现类上, 由 SplitterFactory 构造时自动收集 */
@Target(TYPE) @Retention(RUNTIME)
public @interface ChunkStrategy {
    String key();
    String name();
    String description() default "";
    int maxTokens() default 500;
    int overlap() default 0;
}
```

- `SplitterFactory`: 改为注入 `List<ChunkSplitter>`(Spring 自动收集全部实现 Bean), 构造时读取每个 Bean 的 `@ChunkStrategy` 注解建 Map(key → splitter + 元数据); `getSplitter(key)` 未命中 → 返回 `auto` 语义的默认解析器(见 4.3.4); 移除硬编码注册与 Semantic 兜底。
- **新增策略 = 新增一个类 + `@ChunkStrategy` 注解, 零改动工厂/入口**。

#### 4.3.3 策略清单(本期交付)

| key | 名称 | 依据 | 说明 |
|---|---|---|---|
| auto | 自动选择 | 内容特征 | 解析后自动判定: 有标题层级→structure; 表格元素占比>40%→table; 条款编号结构→policy; FAQ 结构→faq; 否则 semantic。**默认推荐** |
| structure | 结构切分 | 标题层级 | 按章节子树切块(标题链+段落+表格+图片), 超限按段落/句子折叠。精准度+连贯性基线 |
| parent-child | 父子切分 | 结构+句子 | 父块=章节/大段落(检索单元), 子块=句子组(parentId 指向父块) |
| semantic | 语义切分 | 段落/句子 | 保留现状逻辑(无结构文本兜底), 升级支持 overlap/参数 |
| policy | 条款切分 | 条款编号 | 基于结构树匹配"第X条/X.X/一、二、"编号, 而非纯正则 |
| faq | 问答切分 | 问答对 | 识别问/答对, 无匹配退化为 semantic |
| table | 表格切分 | 表格元素 | 表头注入每行; 行数多时按行区间分块 |
| image | 图片块切分 | 图片元素 | 每个图片生成独立块(描述+上下文), chunkType=IMAGE |

#### 4.3.4 auto 默认解析

- 文档未选策略或选 auto 时: `SplitterFactory` 提供 `AutoSplitter`(内部组合结构检测 → 委派对应策略), 保证未知 key/空值永远有确定行为, 不再静默回退 Semantic。

#### 4.3.5 策略列表接口

- `GET /ingestion/split-strategies`(权限 `ai:knowledge:query`, 与 chunk 管理接口一致): 返回全部已注册策略 `[{key, name, description, defaultParams}]`, 供前端下拉 + 入库校验。

### 4.4 B3: 结构化解析 + 图片识别

#### 4.4.1 ParsedDocument 结构树(新模型)

```java
public class ParsedDocument {
    private String docName;
    private String docType;
    private List<Element> elements;   // 按阅读顺序
    // 元素类型(统一接口 Element, 各实现带 page(页码)、seq(顺序号)、titleChain(父标题链))
    //   HeadingElement { int level; String text; }
    //   ParagraphElement { String text; }
    //   TableElement { List<String> header; List<List<String>> rows; }
    //   ImageElement { String imageRef;  // MinIO URL 或本地临时路径
    //                  String caption;   // 图题(如有)
    //                  String contextBefore; } // 前文摘要(增强时填)
    //   ListElement { List<String> items; }
}
```

#### 4.4.2 解析器矩阵

| 文档类型 | 解析器 | 实现 |
|---|---|---|
| PDF | `MineruParser`(新) | 调 MinerU 服务 → 结构化 JSON → ParsedDocument; 无文本层扫描件由 MinerU OCR 出文字 + 视觉模型兜底理解 |
| WORD / PPT | `OfficeParser`(重构) | Apache POI 直接解析: 段落(带样式标题层级)/表格/内嵌图片/页码 |
| EXCEL | `OfficeParser`(重构) | POI Workbook: 每 sheet 一个 TableElement(header=首行, rows=其余) |
| MD / TXT | `TextParser`(增强) | Markdown 标题层级(# 号); 纯文本按段落 |
| IMAGE | `ImageParser`(新) | 整图 → 视觉模型生成描述(含 OCR 文字) → 单个 ImageElement |

#### 4.4.3 MinerU 集成

- **部署**: MinerU API 服务(镜像 `opendatalab/mineru-api` 或自建 FastAPI 包装)以容器进 `deploy/yudao-cloud-dev/docker-compose.yml`, 挂模型目录, GPU 优先(无 GPU 可 CPU, 速度降级, 由配置开关控制是否启用)。
- **配置**: `yudao.ingestion.parser.mineru.{enabled, base-url, timeout-ms, max-pages}`(默认 enabled=false——环境未部署时自动降级为 POI/PDFBox 文本层解析, 保证开发环境可跑)。
- **调用**: ingestion-server 通过 HTTP(MinerU 上传 PDF → 轮询/同步取结构化 JSON), 失败/超时 → 降级 PDFBox 文本层 + 日志告警, 不阻断入库。
- **产出**: MinerU JSON(标题层级/段落/表格/图片位置/公式) → `ParsedDocument` 转换器(`MineruJsonConverter`)。

#### 4.4.4 图片理解(视觉模型)

- 新增 `ImageProcessor` SPI: `ImageDescription describe(String imageRef, String contextText)`。
- 默认实现 `LlmImageProcessor`: 调 model-server `ModelApi` 的 image 类型调用(OpenAI 兼容 `image_url`), 提示词要求输出: 图片内容描述(中文, 面向检索, 含可检索的实体/数字/条款要点) + 图片中的文字(OCR)。
- `ModelChatReqDTO` 增加可选 `images`(List<String> base64 或 URL), **复用 `ModelApi.chat` 透传**(OpenAI 兼容请求体携带图片字段, 不新增接口); 模型路由 type=image(scenario=*), 未启用 → `ImageProcessor` 返回降级(空描述, 仅保留"所属上下文"文本)。
- 图片来源: PDF(4.4.3 提取)/Office(4.4.2 POI 提取)/IMAGE 文档(整图)。
- 扫描页兜底: MinerU OCR 无有效文本且启用视觉模型时, 整页图走视觉模型描述。

#### 4.4.5 图片检索闭环

- 图片描述块内容 = `[图片] {描述} (来源: {章节标题链}, 第{页码}页)`; `chunkType=IMAGE`; `metadata` 含 `imageRef`(MinIO URL, 图片由入库侧上传 MinIO 后引用)。
- 图片块与文本块一同向量化 → 检索命中后前端展示图片(下载/预览 `imageRef`)。
- 无视觉模型/描述失败 → 该图片生成上下文占位块(`[图片] 见{章节}, 第{页码}页`), 仍可被章节检索命中, 不阻断入库。

### 4.5 B4: 上下文增强(精准度 + 连贯性通用机制)

所有策略切分完成后统一执行(在 `SplitterFactory` 内部包装或独立 `ContextEnricher` 组件):

1. **标题链注入**(默认开): 每个 chunk 内容前加 `[{文档名} > {章} > {节}] ` 前缀(来自元素 titleChain; 文档名超过 20 字截断); `titleChain=false` 时跳过。
2. **相邻合并**: chunk 内容低于 `maxTokens*0.5` 时, 与相邻(优先前驱)同类元素合并(段落级), 避免碎片化; 表格/图片块不合并(保结构)。
3. **图片上下文绑定**: `ImageElement.contextBefore` = 前驱段落/章节标题链(前 200 字摘要), 注入图片描述提示词与图片块内容。
4. **overlap**: 连续文本块间按句子重叠(默认 0, 可配 1~2), 缓解边界切分丢失关键句。
5. **块大小自适应**: 元素完整保留优先, 超限才在句子边界折叠(不在词/句中间硬切)。

## 8. 风险与开放项

| 项 | 说明 | 缓解 |
|---|---|---|
| MinerU 部署成本 | Python 服务 + 数 GB 模型 + GPU 优先 | 配置开关默认关, 未部署自动降级 PDFBox 文本层, 不阻塞主线; 部署文档单独出 |
| 视觉模型依赖 | 图片质量依赖视觉模型能力 | image 配置可停用, 停用则降级为上下文占位块; 后续可换更强视觉模型 |
| Office 图片提取 | POI 提取 Word/PPT 图片需遍历 XWPFRun/关系, 工作量大 | 本期 Word/PPT 图片提取为尽力而为, 失败只记日志; 重点保证 PDF(专利主场景) |
| 存量文档策略 | 回填后旧 chunk 仍是旧策略切分结果 | 提供"重新入库"入口(现有 retry-extract 链路可复用), 由运营按需重跑 |
| 检索透明性 | 切分改造后 chunk 内容变化, 检索结果会变 | 用 eval 考题集对比指标, 数据说话; 检索链路本身不改 |
| 前端仓库权限 | vben 仓库在会话工作区外 | 涉及前端改动时按需提升沙箱权限或主 agent 直接改 |
