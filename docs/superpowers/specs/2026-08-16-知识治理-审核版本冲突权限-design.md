# 设计文档:知识治理四件套(版本 + 审核 + 冲突裁决 + 权限边界)

> 日期:2026-08-16 · 状态:已获用户确认(2026-08-16 对话审批)
> 前置文档:《3-PRD产品需求文档.md》(BR-002/005/006/008/014)、《AI客服知识库系统-原型.html》、《上下文交接.md》
> 范围:知识平台管理块的治理能力补齐;不包含检索平台的权限强制过滤(BR-007 检索阶段落地)

---

## 1. 背景与目标

当前入库管线是**直通式**:上传 → 解析 → 切分 → 向量化 → 三写 → INDEXED,无审核、无版本、无冲突检测、无权限边界,与 PRD/原型的**受控式管理**(审核→发布→版本→冲突裁决)不一致。本次补齐四项治理能力:

| 能力 | PRD 依据 | 原型页面 | 现状 |
|------|---------|---------|------|
| 版本状态机 | BR-005 | 版本管理 | `ai_doc_version` 表已建,零代码引用;`ai_chunk.version_id` 是文档 id 占位 |
| 分级审核 | BR-006 | 知识审核 | 无,管线直通发布 |
| 冲突检测与裁决 | BR-008 | 审核页·冲突待裁决 | 无 |
| 权限边界 | BR-007(基础)/BR-014 | 知识库列表(KB-004)、权限管理 | `ai_knowledge_base` 无权限/有效期字段 |

**成功标准**:
- 高风险文档(POLICY/PRICE/LEGAL)未经审核不进入 Milvus/ES 索引
- 发布新版本后旧版本自动过期,检索口径只有已发布版本
- 新旧版本同主题冲突条目进入"待裁决",裁决前不发布
- 无权限用户看不到对应知识库及其文档

## 2. 架构与模块归属

依据《6-改造方案》模块拆分,knowledge-server(48084)负责"知识库/文档/版本/审核",故治理能力全部落在 knowledge-server;governance-server(48093)只管成本/审计,不参与。

```
knowledge-server(48084) ← 治理主战场
    ├─ ai_doc_version        版本(状态机接入,接替 chunk.version_id 占位)
    ├─ ai_review_item        审核条目(LLM 抽取,逐条审核,双人复核)
    ├─ ai_conflict           冲突记录(规则粗筛 + LLM 判定 + 人工裁决)
    └─ ai_knowledge_base     + visible_roles(可见角色) / effective_to(有效期)
model-server(48091)         + chat/completions 接口(Feign,LM Studio OpenAI 兼容)
ingestion-server(48085)     管线改造:审核通过后才写 Milvus/ES
```

**调用关系**:ingestion 调 knowledge(文档状态回写 Feign,已有 + 新增 `notifyParsed`);knowledge 调 model(chat 抽取/判定 Feign,新增)与 ingestion(`indexVersion` 三写,新增);审核/裁决动作全部由 knowledge 内聚。

## 3. 数据模型变更(DDL 增量,追加到 knowledge.sql)

### 3.1 `ai_knowledge_base` 增加字段

```sql
ALTER TABLE ai_knowledge_base
  ADD COLUMN visible_roles varchar(512) NULL DEFAULT NULL COMMENT '可见角色ID列表,逗号分隔;空=全部可见' AFTER status,
  ADD COLUMN effective_to datetime NULL DEFAULT NULL COMMENT '有效期至(空=永久)' AFTER visible_roles;
```

### 3.2 `ai_document` 状态扩展

`parse_status` 增加 `REVIEW`(管线完成、待审核)与 `PUBLISHED`(已过审发布);保留 PENDING/PARSING/EMBEDDING/FAILED。语义:
- REVIEW:解析/切分/向量化完成,条目已抽取,含必审条目待人工处理
- PUBLISHED:全部必审条目处理完,已发布(相当于原 INDEXED 的"可检索"终态)

存量 INDEXED 数据迁移:UPDATE 为 PUBLISHED,视为"已发布 V1"(不强制补审)。

### 3.3 `ai_doc_version` 接入 + 扩展

```sql
ALTER TABLE ai_doc_version
  ADD COLUMN conflict_status tinyint NOT NULL DEFAULT 0 COMMENT '冲突状态:0无 1待裁决 2已裁决' AFTER reviewer,
  ADD COLUMN review_result varchar(16) NULL DEFAULT NULL COMMENT '审核结果: APPROVED/REJECTED' AFTER conflict_status,
  ADD COLUMN review_comment varchar(512) NULL DEFAULT NULL COMMENT '审核意见' AFTER review_result;
```

状态机:`DRAFT → REVIEW → PUBLISHED → EXPIRED/ARCHIVED`。**驳回语义(具体化)**:文档整体驳回 = 版本回 `DRAFT`(可修改后重新提交审核),`review_result=REJECTED` + `review_comment` 留痕;被驳回的必审条目状态为 REJECTED。**同一文档同时仅允许一个 PUBLISHED 版本**,发布时旧 PUBLISHED 自动置 EXPIRED。

### 3.4 `ai_chunk` 增加 embedding 列

```sql
ALTER TABLE ai_chunk
  ADD COLUMN embedding blob NULL DEFAULT NULL COMMENT 'BGE-M3 向量(JSON数组,管线阶段存储,发布时写Milvus)' AFTER content;
```

`version_id` 从"文档 id 占位"改为真实版本 id:管线创建文档时即建 DRAFT 版本,chunk 落库写 version_id = 该版本 id。

### 3.5 新表 `ai_review_item`(审核条目)

```sql
CREATE TABLE ai_review_item (
  id bigint NOT NULL AUTO_INCREMENT COMMENT '编号',
  version_id bigint NOT NULL COMMENT '版本编号',
  doc_id bigint NOT NULL COMMENT '文档编号',
  chunk_id bigint NULL DEFAULT NULL COMMENT '来源Chunk编号',
  item_type varchar(16) NOT NULL COMMENT '类型: POLICY/PRICE/LEGAL/FAQ/SOP',
  title varchar(255) NOT NULL COMMENT '条目主题(如:换屏一口价)',
  content varchar(2000) NOT NULL COMMENT '条目内容(抽取结果)',
  risk_level varchar(8) NOT NULL DEFAULT 'MED' COMMENT '风险: HIGH/MED/LOW',
  ai_confidence decimal(4,3) NULL DEFAULT NULL COMMENT 'AI置信度',
  must_review tinyint NOT NULL DEFAULT 1 COMMENT '是否必审:1必审 0可自动',
  status varchar(16) NOT NULL DEFAULT 'PENDING' COMMENT '状态: PENDING/APPROVED/REJECTED',
  reviewer varchar(64) NULL DEFAULT NULL COMMENT '审核人',
  reviewer2 varchar(64) NULL DEFAULT NULL COMMENT '双人复核第二人(价格类)',
  reject_reason varchar(512) NULL DEFAULT NULL COMMENT '驳回原因',
  review_time datetime NULL DEFAULT NULL COMMENT '审核时间',
  creator/updater/create_time/update_time/deleted/tenant_id   -- 芋道标准字段
  PRIMARY KEY (id), INDEX idx_version(version_id), INDEX idx_doc(doc_id)
) COMMENT 'AI 审核条目';
```

### 3.6 新表 `ai_conflict`(冲突记录)

```sql
CREATE TABLE ai_conflict (
  id bigint NOT NULL AUTO_INCREMENT COMMENT '编号',
  version_id bigint NOT NULL COMMENT '新版本编号',
  old_version_id bigint NOT NULL COMMENT '旧已发布版本编号',
  doc_id bigint NOT NULL COMMENT '文档编号',
  item_id bigint NULL DEFAULT NULL COMMENT '关联审核条目(可空,规则对比产生)',
  title varchar(255) NOT NULL COMMENT '冲突主题',
  old_content varchar(2000) NOT NULL COMMENT '旧版本表述',
  new_content varchar(2000) NOT NULL COMMENT '新版本表述',
  rule_hit tinyint NOT NULL DEFAULT 0 COMMENT '规则粗筛命中:1是',
  llm_judgement varchar(16) NULL DEFAULT NULL COMMENT 'LLM判定: CONFLICT/NO_CONFLICT',
  llm_reason varchar(1000) NULL DEFAULT NULL COMMENT 'LLM判定理由',
  status varchar(16) NOT NULL DEFAULT 'PENDING' COMMENT '状态: PENDING/RESOLVED_NEW/RESOLVED_OLD',
  resolver varchar(64) NULL DEFAULT NULL COMMENT '裁决人',
  resolve_time datetime NULL DEFAULT NULL COMMENT '裁决时间',
  creator/updater/create_time/update_time/deleted/tenant_id   -- 芋道标准字段
  PRIMARY KEY (id), INDEX idx_version(version_id)
) COMMENT 'AI 版本冲突';
```

## 4. 管线改造(审核门禁)

```
上传 → 建文档 + 建版本 V1(DRAFT, version_no 自动递增) → 发 Kafka
  → ingestion 解析 → 切分 → 向量化(BGE-M3)
  → 向量写入 MySQL ai_chunk.embedding【不写 Milvus/ES】
  → knowledge 侧 LLM 抽取审核条目(ai_review_item, 含 must_review/risk_level/confidence)
  → 分流:
     含必审条目(POLICY/PRICE/LEGAL,或 confidence < 0.85)
         → 版本 REVIEW + 文档 REVIEW,进审核台
     无必审条目(FAQ/SOP 且 confidence ≥ 0.85)
         → 自动通过 → 直接发布
  → 发布动作(发布前置检查):
     ① 该版本无未处理完的必审条目: PENDING(待审)与 REJECTED(被驳回)均阻塞发布
        (BR-006: 被驳回的必审条目需"整版驳回回 DRAFT -> 修改/重新抽取"后恢复; 与 §5 驳回语义一致)
     ② 价格类必审条目双人复核完成(reviewer2 非空且不同于 reviewer)
     ③ 冲突检测:对比已发布版本同主题条目 → 有冲突则挂起进"冲突待裁决"
     ③ 通过 → 版本 PUBLISHED + effective_from=now
              + 旧 PUBLISHED 版本置 EXPIRED
              + 从 MySQL embedding 写 Milvus/ES + chunk 置 PUBLISHED
     ④ 存在待裁决冲突 → 版本保持 REVIEW,文档保持待发布,展示冲突列表
```

**发布动作归属**:knowledge-server 的 `VersionService.publish(versionId)` 内聚执行状态流转与门禁检查;**三写(Milvus/ES)由 ingestion 执行**:knowledge 调 `ingestionApi.indexVersion(versionId)`(ingestion 已有 Milvus/ES 存储组件,从 MySQL 读 chunk+embedding 写索引并置 chunk PUBLISHED)。ingestion 不再自行在管线中写 Milvus/ES。

**抽取动作归属**:ingestion 管线末尾(MySQL 落库后)调 `knowledgeApi.notifyParsed(docId)`;knowledge 收到后拉取该版本 chunk 列表 → 调 model-server chat 接口逐批抽取审核条目 → 按规则分流 REVIEW / 自动发布。

**降级**:LLM 抽取失败 → 文档置"抽取失败"状态(FAILED + error_msg),人工可重试抽取;LLM 判定不可用 → 冲突仅规则粗筛,转人工判断。

## 5. 审核台(Chunk 条目级,对齐原型)

- **页面**:四个 tab —— 待审核 / 已通过 / 已驳回 / 冲突待裁决
- **条目卡片**:主题、风险徽标(高风险·价格/条款/法务,中风险,低风险)、来源文档+chunk、AI 置信度、抽取模型
- **操作**:
  - ✓ 通过:状态 → APPROVED,记录 reviewer
  - ✗ 驳回:必填原因,状态 → REJECTED
  - **价格类(PRICE)双人复核**:APPROVED 后需第二个不同审核人再次确认才视为完成(reviewer2),原型"价格变更双人复核"
- **审核策略面板**(原型同款文案):Policy/Price/Legal 必审 · FAQ/SOP 置信度≥0.85 自动 · 价格双人复核 · 置信度<0.85 强制人工
- **入口**:审核台独立菜单 + 文档列表"审核中"状态列点击进入该文档审核

**分级规则落点(与 BR-006 对应)**:
- 条目抽取时由 LLM 输出 item_type/risk_level/confidence,must_review 由规则计算:type ∈ {POLICY, PRICE, LEGAL} → 必审;confidence < 0.85 → 必审;否则可不审

## 6. 冲突检测与裁决(规则粗筛 + LLM 判定 + 人工裁决)

**触发**:发布动作前,对新版本必审条目集合,与已发布版本同主题条目对比。

- **规则粗筛**:title 关键词重合(分词/关键词交集非空)且文本相似度 < 阈值(如 0.85,编辑距离/公共子串) → 候选冲突
- **LLM 判定**:候选条目对交给 model chat 接口,判定 CONFLICT/NO_CONFLICT + 理由(能识别"碎屏免费修"vs"碎屏不免费"同主题反义);NO_CONFLICT 放行
- **裁决**:CONFLICT → ai_conflict.status = PENDING,版本挂起;负责人裁决:
  - 以新版为准(RESOLVED_NEW)→ 继续发布流程
  - 以旧版为准(RESOLVED_OLD)→ 驳回新版发布
- **裁决前口径**(BR-008):检索仍按旧已发布版本;该主题转人工优先(检索阶段落地,本次仅保证旧版仍在检索)

## 7. 权限边界(知识库绑定可见角色)

- **配置**:知识库表单新增「可见角色」多选(复用芋道 role 体系,存 id 逗号分隔)+「有效期至」
- **强制**:
  - 知识库列表 / 文档列表查询:按当前用户角色过滤(无权限知识库不可见,含"全部可见"空值=不限制)
  - 文档详情、Chunk 列表同样透传过滤(通过文档→知识库归属判断)
- **检索过滤(BR-007)**:检索平台阶段复用同一字段,本次不做
- **有效期**:过期知识库视为停用(列表灰显/不可上传新文档),由查询层过滤

## 9. 实施顺序(单个计划,分 4 阶段)

1. **地基**:DDL 增量 + 版本状态机接入(VersionDO/Service/Mapper/Controller)+ chunk.version_id 修正 + embedding 列 + 存量数据迁移
2. **审核**:model-server chat 接口 → 条目抽取(LLM)→ ai_review_item 落库 → 审核台后端 API + 前端页面 → 管线接审核门禁(改三写时机)
3. **冲突**:规则粗筛 + LLM 判定 + ai_conflict + 裁决 API/页面
4. **权限**:知识库 visible_roles/effective_to 字段 + 表单 + 列表过滤

## 11. 已知权衡(用户已确认)

- 条目抽取新增 LLM 调用链(model chat);失败降级:重试抽取/规则降级
- 高风险文档上传后不再是秒级 INDEXED,需审核动作(流程变化,符合 PRD/原型)
- 存量 INDEXED 数据按"已发布 V1"迁移,不强制补审
- LLM 判定失败时冲突检测降级为纯规则 + 人工
