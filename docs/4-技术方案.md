## 1. 文档定位

本文档回答"系统怎么建"的问题,面向架构师、后端/前端/算法/运维工程师。PRD 定义"做什么"(模块、规则、验收),本文定义"怎么做"(架构、技术栈、服务划分、数据设计、部署运维)。两者配套使用:每个 PRD 模块在本文都有对应的技术设计与服务归属。

## 2. 架构设计原则

来自用户文档的核心判断,作为一切技术决策的出发点:

1. **这不是一个 RAG 项目,而是企业 AI 客服平台**。RAG 只是"检索平台"的一部分,LLM 也不是系统的核心。真正的核心是 **知识 → 检索 → 证据 → 业务规则 → AI 生成 → 评测** 这条闭环。
2. **平台化划分**。系统由 7 个平台组成:知识平台、检索平台、证据平台、AI 运行时、Agent/流程平台、评测平台、治理平台,另加客服工作台与多渠道接入。
3. **避免过度设计,但向量库一步到位**。基于用户决策,向量库**直接纳入 Milvus**(不采用"先 pgvector 再迁移"的分阶段路线),为千万级规模预留;其余组件按需演进,不堆砌技术栈。
4. **异步优先**。文档入库等重活全部走 Kafka 异步,上传不阻塞。
5. **AI 只决策、不直控业务**。资金类、审批类操作一律经工具权限 + 工作流执行,全程留痕。
6. **质量与安全是硬约束**。答案必须证据可追溯;越权检索 0 容忍;新版本上线必须过评测闸门。

## 5. 数据层设计

### 5.1 PostgreSQL(核心业务 + 知识元数据)

保存:租户、用户、角色、权限、知识库、文档、知识版本、知识状态、Chunk 元数据、Metadata、Policy、Rule、Condition、会话、消息、评测、反馈、检索日志、答案追踪。

核心表清单(与 PRD 数据模型一致,字段明细见 PRD 5.1):

| 表 | 说明 |
|----|------|
| tenant / user / role | 租户、用户、角色(RBAC) |
| knowledge_base / document | 知识库、文档 |
| doc_version | 文档版本(草稿/审核/发布/过期/归档 5 态) |
| chunk | 知识片段(仅存元数据与文本,向量另存) |
| policy / rule / condition | 业务规则与条件(供规则引擎读取) |
| conversation / message | 会话与消息(含引用 citations) |
| evidence / retrieval_log / answer_trace | 证据记录、检索日志、答案追踪快照 |
| evaluation / feedback | 评测任务与反馈 |
| audit_log | 审计日志 |

要点:所有业务表携带 tenant_id;检索日志与答案追踪只追加不覆盖,支撑"客户质疑时完整重放"。

### 5.2 对象存储(MinIO / S3 / OSS)

原始文档与媒体文件不进数据库。保存:PDF、Word、Excel、PPT、图片、扫描件、音频、视频、网页快照。数据库只保存:文件 ID、路径、Hash、版本、来源、上传人、更新时间、状态。

路径规范:`{tenant_id}/{kb_id}/{doc_id}/{version}/{filename}`;上传后计算 SHA-256 用于重复检测。

### 5.3 向量库设计(决策:直接纳入 Milvus)

**决策结论(用户已确认)**:向量库**直接纳入 Milvus**,与 PostgreSQL、Elasticsearch 三库协同,不再采用"先 pgvector、规模大了再迁移"的分阶段路线。

| 组件 | 职责 | 说明 |
|------|------|------|
| PostgreSQL | 业务与知识的"事实来源" | 用户/租户/文档/版本/会话等全部业务数据;向量元数据与 Chunk 文本也在此 |
| Milvus | 向量召回专用引擎 | Chunk 向量(1024d)落 Milvus,承担千万级向量检索、分片、标量过滤(tenant_id、权限、版本状态随向量存储) |
| Elasticsearch | 全文检索 + 过滤 + 融合 | BM25 关键词检索、元数据过滤,并与 Milvus 的向量结果做 RRF 融合;不依赖 ES 的向量字段 |

**混合检索链路(三库分工)**:

```
查询 → BM25 召回(ES)+ 向量召回(Milvus,带租户/权限/版本过滤)
  → RRF 融合 → 重排(Rerank)→ 证据引擎
```

**为什么这样定(利弊权衡)**:

- 好处:一步到位,为千万级规模预留;Milvus 在超大向量集上的检索性能、分片扩展与标量过滤能力最强;避免未来从 pgvector 迁移的二次改造与停机窗口。
- 代价:从首版起就多一个需部署运维的组件(K8s 部署 Milvus 集群),向量数据与业务数据各存一份,入库管线需保证"Chunk 落 PG + 向量落 Milvus + 关键词落 ES"的一致性(由 ingestion-worker 统一编排,写入失败整体重试)。
- 兜底设计:retrieval-service 将向量库抽象为可插拔接口(`VectorStore`),当前实现为 Milvus;若未来向量库需替换(如换 Zilliz Cloud),上层检索编排与混合逻辑不变。

### 5.4 Elasticsearch 索引设计(核心:chunk 索引)

| 字段 | 类型 | 用途 |
|------|------|------|
| chunk_id | keyword | 主键 |
| tenant_id | keyword | 租户过滤(强制) |
| kb_id / doc_id / version_id | keyword | 归属与版本过滤 |
| perm_level / dept_scope | keyword | 权限过滤(ABAC) |
| content | text(analyzer: ik_max_word) | BM25 全文检索 |
| chunk_type / status / effective_from / effective_to | keyword/date | 元数据过滤与版本状态过滤 |
| vector_key(可选) | keyword | 与 Milvus 向量记录的关联键(默认用 chunk_id 关联) |

说明:纳入 Milvus 后,**向量召回由 Milvus 承担**,ES 专注 BM25 全文与元数据过滤,不再依赖 ES 的 dense_vector 字段;检索时 ES(BM25)与 Milvus(向量)并行召回,再 RRF 融合。

检索 DSL 固定拼装:`bool(must[ bm25 ] + filter[ tenant_id, perm, status=PUBLISHED, effective 窗口 ])`,权限过滤是硬过滤,绝不放在算分之后;Milvus 侧以标量过滤(tenant_id、权限、版本状态)做同样约束,两边过滤口径必须一致。

### 5.5 Redis Key 设计

| Key 模式 | 用途 | TTL |
|----------|------|-----|
| `session:{conv_id}` | 会话上下文(多轮) | 会话活跃期 |
| `rl:{tenant}:{api}` | 限流计数 | 1s/1min |
| `lock:{key}` | 分布式锁(索引一致性等) | 按任务 |
| `hotq:{hash}` | 热问答案缓存(Top 200) | 24h |
| `pcache:{prompt_hash}` | Prompt Cache(输入 token 打折) | 按模型 |
| `mres:{query_hash}` | 模型结果缓存 | 按场景 |

| Topic | 生产者 | 消费者 | 说明 |
|-------|--------|--------|------|
| `knowledge-ingest` | 上传服务 | 解析 → 切分 → 向量化 → 索引 各阶段消费者 | 文档入库流水线(阶段失败可重试) |

## 7. 关键链路设计

### 7.1 知识入库管线(异步)

```
上传(返回 task_id) → Kafka → 文档解析(Tika/PDFBox/POI)
  → 扫描件 OCR(PaddleOCR)→ 结构识别(章节/小节/段落/表格/图片)
  → 语义切分(Semantic / Parent-Child / Table / FAQ / Policy 按类型选择)
  → Embedding(BGE-M3,经 Embedding Gateway)→ 三路写入(ES BM25 + Milvus 向量 + PG 元数据)
  → 高风险知识进入人工审核 → 通过后发布 Published(可检索)
```

要点:每个阶段幂等可重试;三路写入(ES + Milvus + PG)必须一致,任一失败整体回滚重试;重复文档按 hash 拦截;OCR 置信度不足进入质量告警人工复核。

### 7.2 问答检索管线

```
用户问题
 → Query Understanding(意图/实体/属性结构化抽取)
 → Query Rewrite(生成多个检索变体)
 → Query Decomposition(复杂问题拆子问题,分别检索后合并)
 → Metadata Filter(租户 + 权限 + 版本 + 生效期,硬过滤)
 → Hybrid Search(BM25 Top20 + Vector Top20 并行)
 → RRF 融合(40 条候选)
 → Rerank(独立服务,Candidate 40 → Top5)
 → Context Expansion / Evidence Assembly
 → Evidence Engine(去重、冲突检测、充分性判断 → answerable?)
 → LLM 生成(问题 + 证据 + Prompt,流式)
 → Claim Verification(逐句断言比对,SUPPORTED 放行 / UNSUPPORTED 重生成或转人工)
 → 带引用输出
```

### 7.3 证据引擎与 Claim 验证

证据引擎输出标准结构(与 PRD BR-009/BR-010 对应):

```
{ "answerable": true, "confidence": 0.94, "evidence": ["chunk_10001", "chunk_10083"], "conflict": null }
```

判定规则:置信度 ≥ 0.75 允许作答;0.5 ~ 0.75 补充证据或转人工;< 0.5 或存在冲突 → 禁止作答转人工。生成后逐句 Claim 验证,重试上限 2 次,仍无证据支撑的断言禁止出现在客户侧。

### 7.4 规则引擎与工作流

硬规则示例(与 PRD BR-011 对应):

```
IF product = 'X100 Pro' AND purchase_days <= 730 AND damage_type = 'QUALITY' THEN 结论 = FREE_REPAIR
```

LLM 结论与规则冲突时以规则为准并记录偏差。退款/换机/赔偿等敏感操作由 workflow-service 执行流程(Flowable),每一步有审批与审计;Agent 只负责识别意图、填写参数,不直控业务(PRD BR-012/BR-013)。

### 7.5 Agent 工具调用链路

```
LLM 决定需要执行的任务
 → Tool Registry(工具权限校验:只读直调 / 写操作需人工确认 / 资金类禁止直连)
 → Workflow(敏感操作走流程)→ Business API(订单/物流/会员/工单/售后)
 → 结果回填对话 + 调用记录落库(tool_call)
```

## 8. AI 运行时设计

### 8.1 模型网关(Model Gateway)

业务代码不直连任何模型 API,统一经网关:

- 路由:按场景/租户/时段选择主模型(如:在线对话 → Qwen-Max;夜间批量 → DeepSeek-V3;法务 → 本地 vLLM 且禁止降级出域)
- 降级:主模型超时/失败自动切换降级池(如 Qwen-Max → DeepSeek-V3)
- 治理:限流、重试、超时、Fallback、Token 计量、成本统计、A/B 测试
- 私有化:vLLM(K8s GPU 节点)提供 OpenAI 兼容接口,负责模型加载、Batch、KV Cache、并发与流式输出

### 8.2 Embedding 与 Rerank

- Embedding Service 统一封装 Qwen Embedding / BGE-M3 / Jina / 商业 API,向量统一 1024d
- Reranker 独立成服务:Candidate 50 → Rerank → Top5;支持 BGE-Reranker、Jina-Reranker、vLLM 私有化

### 8.3 Prompt 管理

Prompt 与代码分离:版本化、灰度发布、A/B 对比、一键回滚;每次问答记录 prompt_version 用于重放(PRD BR-020)。

## 9. 安全设计

| 项 | 方案 |
|----|------|
| 认证 | OAuth2 / OIDC / JWT(Spring Security),支持 SSO |
| 授权 | RBAC(角色矩阵)+ ABAC(属性策略:部门、密级、租户) |
| 知识权限 | 检索强制 Tenant Filter + Permission Filter,越权 Chunk 不可见并告警 |
| 多租户 | tenant_id 贯穿 Document/Chunk/Embedding/Conversation/User/Policy/Rule/Evaluation 全部核心数据 |
| 数据脱敏 | 客户手机号、身份证等展示打码;会话数据加密存储;导出需审批 |
| 审计 | 全操作留痕(操作人/时间/IP/对象/结果),防篡改 |
| 密钥 | KMS / Vault 管理模型 Key、数据库密钥 |
| 合规 | 满足《个人信息保护法》《数据安全法》,等保二级起步 |

## 10. 可观测性设计

- **Trace**:OpenTelemetry 全链路,关键 span 为用户问题 → 理解耗时 → 检索耗时 → 重排耗时 → LLM 耗时 → Token → 答案,接入 Tempo/Jaeger
- **Metrics**:Prometheus 采集(请求量、时延分位、Token 用量、命中率、幻觉率、降级次数),Grafana 看板
- **日志**:Loki / ELK 集中采集,按 trace_id 关联
- **答案追踪快照**:每次问答保存 conversation_id / question / intent / entities / rewritten_query / retrieval_results / rerank_results / evidence / prompt_version / model / model_version / token_usage / latency / answer / citation / user_feedback(PRD BR-020)

| 告警 | 关键指标阈值告警(时延、错误率、降级、预算 80%/100%) |

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 检索效果不达标(答非所问) | 客户体验、信任 | 80% 根因在切分/召回/生成约束;用评测平台量化,按 切片策略 → 召回 → Prompt 顺序排查 |
| 幻觉流入客户侧 | 合规与声誉风险 | 证据引擎 + Claim 验证双闸门;无据一律转人工;全链路可重放 |
| 模型依赖外部 API 不稳定 | 可用性 | 模型网关降级 + 本地 vLLM 兜底;敏感场景强制本地 |
| 多租户数据隔离漏洞 | 严重合规事故 | tenant_id 硬过滤 + 越权拦截审计 + 定期隔离性测试 |
| Milvus 运维与数据一致性 | 额外组件增加运维成本;三库写入可能不一致 | Milvus 由 K8s 统一编排与监控;入库三路写入由 ingestion-worker 编排,失败整体回滚重试;定期对账(向量数 = Chunk 数) |
| 业务系统对接范围不清 | 集成延期 | 阶段 3 前冻结工具清单与 OpenAPI 契约 |
