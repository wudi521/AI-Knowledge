## 1. 目标

实现 AI 客服知识库的**入库管线**:上传的文档(已登记 `ai_document` PENDING)由 ingestion-server 异步消费,完成 **解析 → 切分 → 向量化 → 三写(MySQL + Milvus + ES)**,最终 `ai_document.parse_status = INDEXED`,前端可见状态流转。

## 2. 已确认决策汇总

| 决策点 | 结论 | 说明 |
|--------|------|------|
| 触发方式 | Kafka 异步 | knowledge-server 上传后发消息(`knowledge-ingest` 主题),ingestion-server 消费 |
| 向量模型 | LM Studio `text-embedding-bge-m3` | base_url `http://127.0.0.1:1234/v1`,1024 维,已实测可用 |
| 解析范围 | 全格式 | TXT/MD 直接读;PDF→PDFBox;Word/Excel/PPT→POI;扫描件→Tika+Tesseract OCR |
| OCR | Tika + Tesseract | 本机 tesseract 5.5.2(含中文语言包) |
| 切分策略 | 五策略全实现 | Semantic / ParentChild / Table / FAQ / Policy(PRD BR-003) |
| 索引写入 | MySQL + Milvus + ES 三写 | MySQL 存业务元数据;Milvus 存向量;ES 做 BM25 全文 |
| 代码位置 | 解析+切分全在 ingestion-server | 符合 6-改造方案模块拆分 |
| 前端同步 | kb/knowledge-base 切分策略改为 5 种 | 当前只有 3 种(ParentChild/SlideWindow/Sentence) |

## 3. 总体架构与数据流

```
【上传】(前端 kb/documents)
   │
   ▼
knowledge-server ──► 登记 ai_document (parse_status=PENDING)
   │                 └──► Kafka 发送消息 (knowledge-ingest 主题, payload=documentId)
   ▼
ingestion-server(Kafka 消费者)
   │  ① 解析 DocumentParser(策略模式)
   │     TXT/MD: 直接读文本
   │     PDF: PDFBox 提取(有文本层)/ Tika+Tesseract OCR(扫描件)
   │     Word/Excel/PPT: POI 提取(tika 统一入口)
   │  ② 切分 ChunkSplitter(五策略选择器, 按 ai_knowledge_base.chunk_strategy)
   │  ③ 向量化 EmbeddingClient → Feign 调 model-server → LM Studio BGE-M3 (1024维)
   │  ④ 三写:
   │     MySQL: ai_chunk 行(含 vector_key=chunk_id, tenant_id)
   │     Milvus: collection ai_chunk_vector(1024维, 标量 tenant_id/kb_id)
   │     ES: index ai_chunk_bm25(ik_max_word 分词, tenant_id/status 过滤)
   │  ⑤ 回写 knowledge-server: parse_status = INDEXED / FAILED(+error_msg)
   ▼
前端 kb/documents 展示状态流转(待解析→解析中→向量化中→已入库/失败)
```

## 4. 五切分策略定义(PRD BR-003 落地)

| 策略 | 切分逻辑 | chunk_type | 备注 |
|------|---------|-----------|------|
| **Semantic** | 按段落/标题边界切分,相邻段语义相似度 > 阈值(0.75)时合并 | SEMANTIC | 默认兜底策略 |
| **ParentChild** | 父块 = 大段落(≤2000 token),子块 = 父块内按句/段切(≤500 token);子块带 `parent_id` 指向父块 | SEMANTIC | ai_knowledge_base 默认值 |
| **Table** | 识别表格(行分隔符/单元格),每行为一个 chunk,列名拼入内容 | TABLE | 适用于 Excel/价目表 |
| **FAQ** | 识别"问题+答案"对(问:…答:… / Q:…A:…),成对入库 | FAQ | 适用于问答文档 |
| **Policy** | 按条款编号(第X条 / 1.1 / 一、二、三)边界切分 | POLICY | 适用于政策/条款文档 |

> 切分策略由 `ai_knowledge_base.chunk_strategy` 决定,ingestion 消费消息时先查知识库配置,再用对应策略。

## 5. 三写设计

### 5.1 MySQL(ai_chunk 表,已建)

字段按 `knowledge.sql`:`id / version_id / content / chunk_type / metadata / status / vector_key / tenant_id`。
- 写入:`vector_key = chunk_id`(Milvus 关联键)
- 状态:`PUBLISHED`(默认)

### 5.2 Milvus(collection: ai_chunk_vector)

| 项 | 值 |
|----|-----|
| 集合名 | `ai_chunk_vector` |
| 字段 | `chunk_id`(INT64,主键)、`embedding`(FLOAT_VECTOR, 1024)、`tenant_id`(INT64 标量)、`kb_id`(INT64 标量) |
| 索引 | IVF_FLAT / HNSW,nlist=1024,METRIC_TYPE=COSINE |
| 创建 | ingestion-server 启动时自动 create_collection(if not exists) |
| SDK | milvus-sdk-java 2.4.1 |

### 5.3 Elasticsearch(index: ai_chunk_bm25)

| 项 | 值 |
|----|-----|
| 索引名 | `ai_chunk_bm25` |
| 字段 | `chunk_id`(keyword)、`tenant_id`(keyword)、`kb_id`(keyword)、`status`(keyword)、`content`(text, ik_max_word) |
| 过滤 | 硬过滤 `tenant_id + status=PUBLISHED`,放在算分前(4-技术方案 5.4 一致) |
| 客户端 | elasticsearch-rest-client(high-level)或 spring-data-elasticsearch |

### 5.4 一致性策略

1. 先写 MySQL(ai_chunk),拿到自增 id
2. 再写 Milvus(embedding + chunk_id)
3. 再写 ES(BM25 文档)
4. Milvus/ES 任一失败 → 删除已写 MySQL 记录 + 重试;重试 3 次仍失败 → `parse_status=FAILED` + `error_msg`
5. 幂等:Kafka 消费前查 `ai_document.parse_status` 与 ai_chunk 是否已生成,INDEXED 直接跳过

## 8. 测试与验收

- **单元测试**:五切分策略各一条样例输入→断言 chunk 数量/内容;DocumentParser 每种格式一个样例文件;EmbeddingClient mock LM Studio 返回
- **集成测试**(手动/脚本):
  - `/kb/documents` 上传 TXT/MD/PDF/Word 各一份 → 观察状态流转(PENDING→PARSING→EMBEDDING→INDEXED)
  - 验证三处数据:MySQL `ai_chunk` 行数 > 0;Milvus 集合行数 = ai_chunk 行数;ES 索引行数 = ai_chunk 行数
  - 失败用例:上传损坏文件 → FAILED + error_msg 可见
- **验收标准**:对照 PRD AC-001(上传后 10 分钟内变可检索)、BR-004(三写一致性)
